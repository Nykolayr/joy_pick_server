# Концепция партнёров: роли, филиалы, продавцы, списание коинов

Документ для фронта и админки: роли, потоки, структура БД и API.

---

## 1. Роли

| Роль | Вход | Где работает |
|------|------|--------------|
| **Админ партнёра** | Отдельная форма входа (кнопка «Вход для партнёров»). Логин = email партнёра, пароль задаётся при создании партнёра (генерируется на фронте). | Та же админка, но после входа — только разделы партнёра: филиалы, продавцы, история списаний, настройки (валюта, курс, смена пароля). |
| **Продавец партнёра** | Отдельный эндпоинт входа (логин + пароль из таблицы продавцов). | Приложение для продавца: выбор филиала, сканирование QR волонтёра, ввод суммы списания коинов, списание. |

Обычные пользователи (волонтёры) входят как раньше и в приложении получают QR для предъявления в филиале партнёра.

---

## 2. Партнёр (расширение текущей таблицы)

Текущая таблица `partners`: id, name, logo_url, photo_urls, activity, website_url, created_at, updated_at. Адрес и координаты у партнёра отсутствуют — они задаются только у филиалов (таблица `partner_branches`).

**Добавить поля:**

| Поле | Тип | Описание |
|------|-----|----------|
| `admin_email` | varchar(255) NULL | Email админа партнёра = логин для входа в админку. |
| `admin_password_hash` | varchar(255) NULL | Хеш пароля админа (bcrypt). Пароль задаётся при создании партнёра (генерация на фронте), можно менять в кабинете. |
| `currency` | varchar(10) NOT NULL DEFAULT 'USD' | Валюта скидки (USD, RUB и т.д.). |
| `exchange_rate_cents_per_coin` | int NOT NULL DEFAULT 50 | Сколько центов (или младших единиц валюты) даёт 1 коин. Пример: 50 → 1 коин = 0.50 USD. |

При создании партнёра суперадмин (или админ) задаёт/генерирует пароль админа партнёра; логин админа = email партнёра (или отдельное поле `admin_email`).

## 3. Филиалы партнёра

Один партнёр — много филиалов (магазин, кафе «Луна» и т.д.).

**Таблица `partner_branches`:**

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | varchar(36) | PK, UUID. |
| `partner_id` | varchar(36) | FK → partners.id. |
| `name` | varchar(255) | Название (например, «Кафе Луна»). |
| `address` | text | Адрес. |
| `latitude` | decimal(10,8) NULL | Широта. |
| `longitude` | decimal(11,8) NULL | Долгота. |
| `created_at` | timestamp | |
| `updated_at` | timestamp | |

Продавец при входе в приложение выбирает филиал, в котором сейчас работает. При списании коинов в транзакции сохраняется выбранный филиал.

## 4. Продавцы партнёра

**Таблица `partner_sellers`:**

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | varchar(36) | PK, UUID. |
| `partner_id` | varchar(36) | FK → partners.id. Один продавец — один партнёр. |

| `login` | varchar(255) | Логин для входа. Уникальность только в рамках партнёра (один и тот же login может быть у продавцов разных партнёров). |
| `password_hash` | varchar(255) | Хеш пароля (bcrypt). |
| `job_title` | varchar(255) NULL | Должность. |
| `created_at` | timestamp | |
| `updated_at` | timestamp | |

Уникальный индекс: `(partner_id, login)` — один логин на партнёра.

## 5. Списание коинов (транзакции)

Каждое списание сохраняется у партнёра и у волонтёра.

**Таблица `partner_coin_redemptions` (или `coin_redemptions`):**

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | varchar(36) | PK, UUID. |
| `partner_id` | varchar(36) | FK → partners.id. |
| `branch_id` | varchar(36) | FK → partner_branches.id. Филиал, где произошло списание. |
| `seller_id` | varchar(36) | FK → partner_sellers.id. Продавец, который провёл списание. |
| `user_id` | varchar(36) | FK → users.id. Волонтёр, у которого списали коины. |
| `coins_spent` | int | Сколько коинов списано. |
| `amount_cents` | int | Сумма скидки в центах (или в младших единицах валюты). По курсу партнёра на момент списания. |
| `currency` | varchar(10) | Валюта (копия или из партнёра). |
| `created_at` | timestamp | Дата/время списания. |

Этой таблицы достаточно и для «истории у партнёра», и для «истории у волонтёра»: выборки по `partner_id` или по `user_id`.

Дополнительно в `users` можно не добавлять отдельное поле «транзакции» — список списаний по волонтёру берётся из этой же таблицы по `user_id`. Если нужно хранить в пользователе агрегат (например, «всего списано коинов за всё время») — можно добавить поле `jcoins_spent_total` или считать на лету из `partner_coin_redemptions`.

---

## 6. История у волонтёра (приложение)

История списаний коинов для волонтёра = выборка из `partner_coin_redemptions` по `user_id`, с подставой названия партнёра, филиала, суммы скидки, даты. Отдельная таблица не нужна.

При необходимости в таблице `users` можно добавить поле только для счётчика/агрегата (например, `total_coins_redeemed`), но не обязательно — можно считать по таблице списаний.

## 7. QR-код волонтёра

- QR формируется на бэкенде.
- В QR зашиваются данные, позволяющие однозначно идентифицировать волонтёра и при этом **одноразовость**: один и тот же QR нельзя многократно использовать для списания.
- Вариант реализации:
  - Бэкенд отдаёт эндпоинт вида `GET /api/partners/volunteer-qr` (с JWT волонтёра). Ответ: одноразовый токен (или подписанный payload: `user_id` + `nonce`/`timestamp` + подпись). Срок жизни короткий (например, 1–2 минуты).
  - В QR кодируется этот токен (или URL с токеном).
  - Продавец сканирует QR, приложение продавца отправляет токен на бэкенд.
  - Бэкенд проверяет подпись и одноразовость (nonce/время или пометка «токен использован»), возвращает данные волонтёра: id, ФИО (first_name, second_name, display_name), текущее количество коинов (`jcoins`). После успешного списания токен помечается использованным или считается истёкшим.

Итог: каждый показ QR в приложении волонтёра = новый запрос к бэку и новый токен, повторное использование старого QR не принимается.

## 8. Поток списания коинов (сценарий)

1. Волонтёр в приложении запрашивает QR (запрос к бэку с JWT) → получает одноразовый токен/QR.
2. Волонтёр приходит в филиал, показывает QR. Продавец в приложении партнёра выбирает филиал (если ещё не выбран), сканирует QR и отправляет токен на бэк.
3. Бэк по токену возвращает: id волонтёра, ФИО, количество коинов. Ограничений по лимиту списания нет; продавец не может списать больше, чем есть у волонтёра (фронт/приложение продавца показывает баланс и не даёт ввести больше).
4. Продавец вводит количество коинов для списания и нажимает «Списать».
5. Запрос на бэк: партнёр (или продавец), филиал, продавец, волонтёр (user_id), количество коинов. Бэк:
   - проверяет токен/сессию продавца и принадлежность партнёру/филиалу;
   - проверяет, что у пользователя достаточно `jcoins`;
   - списывает коины у пользователя (`UPDATE users SET jcoins = jcoins - ? WHERE id = ?`);
   - создаёт запись в `partner_coin_redemptions` (партнёр, филиал, продавец, волонтёр, coins_spent, amount_cents по курсу партнёра, валюта, created_at);
   - возвращает успех и сумму скидки в валюте (например: «Скидка 2 USD»).
6. Продавец уменьшает сумму к оплате на размер скидки.

Курс при списании берётся текущий у партнёра (`exchange_rate_cents_per_coin`): amount_cents = coins_spent * exchange_rate_cents_per_coin. История хранит фактически списанные coins и amount_cents; при смене курса старые записи не меняются.

## 9. Авторизация

- **Админ партнёра:** отдельный эндпоинт, например `POST /api/partner-auth/admin/login` (email + password). В ответ — JWT с типом «partner_admin» и partner_id. В админке по этому JWT показываются только разделы и данные этого партнёра.
- **Продавец:** `POST /api/partner-auth/seller/login` (login + password). В теле или query передаётся partner_id (или партнёр определяется по логину после проверки пароля). В ответ — JWT с типом «partner_seller», partner_id, seller_id. Далее запросы списания идут с этим JWT.

На странице входа админки — кнопка «Вход для партнёров», по нажатию переход на форму входа админа партнёра (email + пароль). После успешного входа — редирект на разделы админки для партнёра (филиалы, продавцы, история списаний, настройки).

---

## 10. Что видит админ партнёра в кабинете

- Филиалы: список, добавление/редактирование (название, адрес, координаты).
- Продавцы: список, добавление/редактирование (ФИО, логин, пароль, должность).
- История списаний: таблица по своему партнёру — дата, филиал, продавец, волонтёр (ФИО или id), сколько коинов списано, сумма скидки в валюте.
- Настройки: валюта, курс (1 коин = X центов), смена пароля админа партнёра.

---

## 11. Что видит волонтёр в приложении

- Текущий баланс коинов (уже есть).
- Кнопка «Показать QR для скидки» → запрос к бэку → отображение QR (одноразового).
- История списаний: список транзакций из `partner_coin_redemptions` по своему `user_id` (партнёр/филиал, дата, списано коинов, сумма скидки).
